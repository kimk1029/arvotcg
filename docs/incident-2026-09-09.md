# 2026-09-09 DB 연결 풀 고갈 장애 및 재발 방지

조사일: 2026-09-10. 아래 타임라인은 KST. 운영 서버의 PM2 로그와 Git 이력을 대조했다.

## 원인과 영향

무거운 최신 시세 조회와 반복 쓰기가 공유 DB 연결 풀을 오래 점유하면서
P2024(연결 획득 시간 초과)가 발생했고 로그인·컬렉션을 포함한 API에 장애가 전파됐다.
서버 프로세스가 살아 있어도 DB를 쓰는 기능은 실패할 수 있는 장애였다.

운영 PM2 `pokefesta30-server-error-112.log`에서 P2024 문자열 471회를 확인했다.
이 파일 최종 수정 시각은 9/9 19:05:17이며, 오류는 pool_timeout=10,
connection_limit=10을 명시한다. 이는 **로그 문자열 출현 수**로, 실패 요청 수나
영향 사용자 수와 같지 않다. 기존 로그에 항목별 타임스탬프가 없어 정확한 최초 발생
시각·연속 중단 시간은 확정하지 못했다. 따라서 23:57 변경만을 최초 원인으로 단정하지 않는다.

`e45bdeb` 커밋에는 당시 pg_stat_statements 조사 결과가 기록돼 있다:
랭킹 두 쿼리가 DB 디스크 읽기의 78%(54GB), 누적 DB 시간 8시간 44분을 차지했고,
78만 행/465MB의 이력에서 매번 최신 시세를 찾았다. shared_buffers는 224MB였다.
이 수치는 **당시 작업자가 커밋에 남긴 측정값**이며 이번 조사에서 재측정한 값은 아니다.

## 기존 보호 장치 — 현재 코드에서 확인

- 현재가는 `snkrdunk_current_prices`에서 조회, 이력은 차트 등에 사용.
- `DailyCache`: 동시 요청 합치기, 오래된 캐시 유지, 실패 후 60초 재시도 유예.
- `priceWork`: 프로세스당 갱신 동시성 1, 대기열 500개 제한.
- 랭킹 DB 쿼리에 statement_timeout 3초, 트랜잭션 대기/실행 한도.
- 일일 배치 대상 최대 500개. 동일 가격 스냅샷 반복 기록 억제.

## 이번 추가 조치

1. `/ready`: 실제 앱 DB 풀로 현재가 테이블을 조회한다. 실패·시간 초과 시 HTTP 503.
   SQL 1.5초, 트랜잭션 2초/획득 대기 1초, 응답 대기 2.5초 한도.
   결과는 5초 캐시하며 진행 중 쿼리는 하나만 유지한다. 응답 시간이 초과돼도
   실제 쿼리가 끝날 때까지 추가 쿼리를 만들지 않아 감시 자체의 풀 고갈을 방지한다.
   테이블이 비어 있는 것은 정상으로 처리한다. 데이터 신선도나 모든 API의 정상까지 보장하지 않는다.
2. 서버 배포 전 장애 회귀 테스트를 필수 실행하고, 통과한 정확한 Git SHA를 배포한다.
   배포 후 `/ready` 성공을 확인한다. 기존 `/health`는 DB를 확인하지 않아 배포 검증에 불충분했다.
3. GitHub Actions `Production availability`: 5분 cron으로 `/ready`를 확인한다.
   요청마다 5초 제한, 10초 간격으로 총 3회 실패 시 작업 실패를 기록한다.
   대상은 `shared/apiEndpoints.ts`의 운영 주소이며 저장소 변수 `MONITOR_API_ORIGIN`으로 변경 가능하다.
   Actions 스케줄은 지연될 수 있으므로 5분 이내 감지를 보장하지 않는다.
   메일·Slack 등 별도 발송 연동은 추가하지 않았다. 실패 알림 수신은 GitHub 개인 알림 설정에 달려 있다.
4. PM2 서버 로그에 타임스탬프를 활성화해 후속 장애의 발생·복구 시각을 확인할 수 있게 한다.
5. 회귀 테스트: DB 실패/복구, 쿼리 무응답 중 50개 동시 헬스 요청, 정상 결과 캐시,
   갱신 큐 포화/오류 후 회복, 시세 캐시 동시 요청 합치기/DB 장애 중 기존 값 유지.

## 운영 대응 절차

- `/ready`가 503이면 어드민 시스템 상태에서 DB 연결 수·최장 실행 쿼리·누적 부하를 확인한다.
- PM2 로그를 먼저 보존하고 P2024·P2028·P2010 발생 시각과 최근 배포 SHA를 대조한다.
- 풀 개수만 올리지 않는다. 비필수 배치/갱신 부하를 줄이고 느린 쿼리·락을 먼저 확인한다.
- 코드 회귀라면 현재가 테이블을 지원하는 검증된 버전으로 되돌린다.
  DB 스키마를 무조건 되돌리거나 프로세스를 반복 재시작하지 않는다.
- 복구는 `/ready`, 공개 랭킹 응답, 로그인 및 컬렉션 조회로 확인한다.
  로그인 검증에는 실제 테스트 계정이 필요하며 이번 조사에서 사용자 계정으로 로그인하지 않았다.

## 검증 및 한계

로컬 루트/server/mobile TypeScript 검사 통과. 장애 회귀 테스트 5개 통과.
수정 전 운영 `/health` HTTP 200(28ms), 공개 랭킹 HTTP 200(176ms)를 직접 확인했다.
현재 운영 프로세스는 dbd8c11 기준 약 6시간 실행 중이며 최신 error-147 로그에서
P2024가 없었다. 외부 KREAM 등 별도 오류는 남아 있으므로 모든 기능 무오류라는 뜻은 아니다.

이번 조치는 같은 유형의 회귀를 줄이고 DB 장애 감지 누락을 막는다. 모든 DB 작업에
전역 실행 시간 제한을 적용하거나 DB 자원을 완전히 격리한 것은 아니다.
서버 배포는 여전히 실행 디렉터리에서 npm ci 후 delete/start하므로 짧은 중단과
실패 시 수동 복구 위험이 남는다. 별도 릴리스 디렉터리·자동 롤백 전환은 추가 작업이다.
